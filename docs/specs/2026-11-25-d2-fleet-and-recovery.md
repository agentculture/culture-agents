# D2 fleet and recovery

> culture-agents runs a small fleet without losing track of work: two runs can work in one repository at once, a restarted core takes back live control of the workers that survived it, a duplicate submit is answered once, work is placed only on a host that can take it, a halted host is never reported as a success, and a question a run asks its operator is still waiting after a restart.

## Audience

- Operators and calling agents (the agents CLI today; culture-rules and embodiment later) that submit work to more than one culture-agents host and need the state they read to stay true across restarts and host failures.

## Before → After

- Before: Today (D1, control API 2.0), a restarted core reads a surviving worker's state from disk but cannot steer, cancel or attach to it: reconnectWorker exists (core/src/worker/spawn.ts:201) and only tests call it. A second submit to a repository with an active run is refused as busy (core/src/runs/service.ts:117-129). The idempotency key is stored on the run (core/src/runs/service.ts:141) and never compared. 'answer' is always refused as unsupported (contract/api.json:477-480). The API is served on one Unix socket on one host. Nothing lists or removes `runs/<id>` branches.
- After: After part one, on one host: a core that restarts steers, cancels and attaches to the workers that outlived it; one repository holds several active runs up to a stated bound; a repeated submit, steer or cancel with the same idempotency key takes effect once; a run's question to its operator is on disk and answerable after a restart; finished run branches can be listed and removed with evidence. After part two: the same control API is reachable on more than one host, a submit is admitted only where the host can take it, and a run on a halted host reads 'unknown'.

## Why it matters

- Issue #2 allows archiving agent-lifecycle and cultureagent only after this repository passes recovery tests, and D3 to D5 (chat, culture-rules, embodiment) will submit work to it without a person watching. A caller that retries after a timeout, or reads state after a restart, has to get a true answer: one run, not two, and never a success the core did not observe.

## Requirements

- After a core restart, the core takes back live control (steer, cancel, attach) of every worker that survived it. reconcile() rebuilds the in-memory controls map through the existing reconnectWorker, and the 'reconnect' capability stops being refused.
  - honesty: Reattach is proven by killing the core process (SIGKILL, not a clean stop) while a stub-harness run is mid-turn, starting a new core, and observing a steer and a cancel take effect on that run. A worker whose control socket no longer answers is reported 'unknown', never reattached by guess.
- Two or more runs can be active in one repository at the same time, each steered independently. No limit applies unless the operator configures one; a configured limit is a check at submit. The one-active-run-per-repository 'busy' rule is removed, and the '`worktree_isolation`' capability reports what is actually guaranteed.
  - honesty: Two concurrent runs in one repository each return commits only on their own `runs/<id>` branch, and neither branch contains the other's commits. The bound is a number a caller can read, and a submit past it gets a typed refusal, not a queue that is silently created.
- A duplicate submit with the same idempotency key returns the first run instead of starting a second one, and the same key with a different request is refused as a conflict. Steer and cancel deduplicate on their keys the same way. The key index is on disk, so it holds across a restart.
  - honesty: The key index is written to disk before the submit is acknowledged, so a crash between the two cannot produce a second run for the same key. The comparison that decides 'same request' is stated in the contract, including how long a key is remembered.
- A run can ask its operator a question and wait. The question is written to the run's on-disk log, is still pending after a core restart, and 'agents runs answer' delivers the answer into the same run. A harness that cannot ask says so in its capability report.
  - honesty: At least one real harness can ask and wait without allow-all approvals. docs/d0/probe.md:286-295 lists approvals as unverified in the AI SDK adapter, so this requirement is conditional on a probe that runs before the plan; if no harness can ask, the capability is reported unsupported and the requirement is cut down to the store and the 'answer' verb against the stub.
- A submit names where the work may run, and the core admits it only when that host can take it: the harness is available, a configured limit has room, and the host's heat signal does not say hold. The model-gateway signal joins the check for harnesses that use the gateway once lobes publishes an admit field with a timestamp; D2 ships without waiting for it. A signal that is missing or stale reads as unknown: a remote submit is refused and a local one is admitted with a warning. An unknown signal is never a hard failure of the control plane.
  - honesty: The heat signal is read as heat-governor publishes it, with no change there. The gateway signal is read only from the admit field that the lobes issue adds; until a lobes release has it, the gateway signal is not consulted and the capability report says so.
- When a host halts or cannot be reached, every run that was active on it reads 'unreachable' to every caller, and never 'succeeded'. 'unreachable' is a view, not a stored state: the stored terminal state 'unknown' is still written only by the owning core, as on one host.
  - honesty: A halted host is detected by something that can be tested (a missed heartbeat or a failed request with a stated timeout), and the reader's answer never changes a run's stored terminal state: 'unknown' is a view until the host returns and reports.
- Finished runs stop accumulating: there is a way to list the `runs/<id>` branches a repository holds, and a rule for removing one that requires positive evidence its commits are kept elsewhere (merged, or on another ref). Unknown liveness defers removal; nothing is force-deleted.
  - honesty: Removal never runs 'git branch -D'. The evidence rule (merged into a named ref, or reachable from another ref) is checked by git itself, and a branch whose run is 'unknown' or still retained is skipped and listed as skipped.
- The three recovery gaps recorded after D1 are closed: a cancel whose grace period ends during retention cleanup still leaves a retention record, the worker's 'conflict' reply on a refused append has a test, and the daemon installs its signal handlers before it reports that it is listening.
  - honesty: Each of the three gaps has a test that fails on today's main and passes after the fix: late cancel during retention cleanup still leaves a retention record; the worker's 'conflict' reply; signal handlers installed before the 'listening' log line (core/src/daemon/main.ts:135-139).
- A core announces itself as a fleet member when it starts and stops being listed when it stops or goes silent. Callers discover members from those announcements; no list of hosts is kept in the repository or in a tracked file.
  - honesty: A test starts two cores, sees each list the other after its announcement, stops one, and sees it leave the list within a stated number of seconds while its active runs read 'unknown' (c9), not removed.
- Every run event the core appends to a run's log is also published to the existing broker (events-cli), in the envelope that broker's consumers already read. Publishing is best effort and comes after the on-disk append: the log stays the source of truth, a subscriber that missed events catches up from the log by cursor, and a broker that is down or slow never blocks, fails or delays a run.
  - honesty: A test runs a run to completion with the broker stopped and gets the same terminal state and the same event log as with the broker up; a second test subscribes, drops the connection mid-run, and recovers every missed event from the log by cursor with no duplicate.
- Each run records who submitted it, as the core established it and never from a request field: for a local call, the user that owns the control socket; for a call from another host, the authenticated fleet member. The field is in the run's contract shape. Part one does not enforce on it; part two's ownership rules read it.
  - honesty: No request field can set or change the submitter; for a local call it equals the user that owns the socket, for a remote call the member the connection authenticated as. This replaces h24.
- Local callers are authenticated by the operating system through file permissions: the control socket is owner-only (mode 0600 in a 0700 directory), so only the user that runs the core can connect, and no password or token is used locally. Reading the peer user of each connection is not part of D2.
  - honesty: A test connects as a different operating-system user and is refused by the file system, before the core sees a request; the socket and its directory keep modes 0600 and 0700. This replaces h25.
- Cores on different hosts authenticate each other with key pairs, not a shared secret: each core has its own private key, peers hold only its public key, and the connection between two cores is encrypted and mutually authenticated. No secret that grants membership is ever sent over the network, and one host's key gives no access as any other host.
  - honesty: A test shows a core with an unknown key is refused, a core whose key was removed from a peer's trust list is refused on its next connection, and a packet capture of a join contains no private key and no reusable secret. The private key reaches the daemon through grant at start and is not written to a tracked file, a log or an event.
- A remote submit names the repository as the executing host knows it (that host's allow-listed path, or an alias the host defines), and a run's commits can be fetched from the executing core through the control API as a git bundle, so a caller on another host can bring the `runs/<id>` branch home without shell access to that host.
  - honesty: A test submits from host A to host B, fetches the result bundle through the API on A and verifies it with 'git bundle verify'; the bundle route serves only refs under `runs/<id>` of a run the caller may read.
- Two fleet members never share a node name: an announcement from a core whose node name is already held by a different key is refused and reported. Run ids stay `<node>-<agent>.run.<ULID>`, so the node part of any run id names the host that owns it.
  - honesty: A test starts a second core with the first one's node name and a different key and sees its announcement refused; no run id minted by one member can be minted by another.
- Each member's capability report states its configured limits (or that none is set), how many runs are active, and its admission state per signal (admit, hold or unknown), so a caller that must choose a host can do so from the API. The caller chooses the host; D2 has no scheduler.
  - honesty: The fields are in contract/capabilities.json and a test reads them from two members; the report never shows another host's data.
- A deadline sent to another host is evaluated on the executing core's clock from a duration, not from the caller's absolute time, and ordering across hosts never relies on comparing two hosts' clocks. Order within a run stays the cursor.
  - honesty: A test submits with the caller's clock set several minutes off and the run gets the full requested duration; no code compares a timestamp from one host with a clock on another.
- The agents CLI sends an idempotency key on every submit, steer and cancel (generated when the user gives none) and, after a timeout, retries with the same key instead of telling the user to retry by hand.
  - honesty: A test drops the response of a submit and sees the CLI's retry return the first run; the 'unavailable' hint no longer suggests a bare retry for a request that may have been accepted.
- The core removes its fleet private key and every other injected secret from the environment before it spawns a worker or runs a host command; no worker, sandbox or harness process can read them.
  - honesty: A test starts the core with a marker secret injected, submits a run and shows the marker is absent from the worker's environment and from the sandbox. Today a worker inherits process.env (core/src/worker/spawn.ts:168) and host commands filter only `GIT_`\*, `GH_TOKEN`, `GITHUB_TOKEN` and `SSH_AUTH_SOCK` (core/src/sandbox/host-command.ts:29-39).
- Published run events use a type prefix of their own with at most four segments (for example agents.run.finished), an id derived from the run id and cursor so a republished event has the same id, and the run's cursor in the envelope so a consumer can resume from the log.
  - honesty: culture-rules subscribes to every type of up to four segments and already owns rules.run.\* (`culture_rules`/events/emit.py:80, `events_cli_adapter.py`:58-66); a test publishes each run event type and reads it back through an events-cli subscriber, and publishing the same event twice yields one id.
- A caller that cannot reach a member shows that member's runs as 'unreachable', a view that is never stored. The terminal state 'unknown' is written only by the core that owns the run, when it has evidence that the worker is gone. A run shown as unreachable can still end in any terminal state once its host answers.
  - honesty: A test partitions two hosts while a run is active, sees 'unreachable' on the caller, heals the partition and sees the run's real terminal state; no terminal state was written by the caller's side.
- Two cores on different minor versions of the same API major can call each other in both directions; the version rule for core-to-core calls is stated in the contract, and a rolling upgrade of the fleet never needs all hosts to change at once.
  - honesty: Today's rule is 'same major and server minor at least the client minor' (contract/README.md:91-92), which fails in one direction between two cores at different minors; a test runs a 3.0 core against a 3.1 core in both directions.
- A restarted core finishes reattaching before it answers control requests for a run: until a run's reattach attempt has completed, a steer, cancel or attach for it waits or is answered 'retry shortly', never 'live control unavailable'. Controls of runs that are already terminal are not rebuilt.
  - honesty: Today the daemon listens before reconcile() runs (core/src/daemon/main.ts:113 against :120) and each reattach can take up to 1 second (core/src/worker/spawn.ts:201); a test sends a steer in the first second after a restart with several live runs and it takes effect.
- A submit that was in flight when the core died is accounted for after the restart: its worker, if one was spawned, appears as a run, and a repeat of the same idempotency key returns that run. The order on disk is key first, then the run directory, then the spawn; a key whose run was never established is released, and run directories without a first event and leftover temporary files are removed at startup.
  - honesty: A test kills the core at each step of a submit (after the key, after the run directory, after the spawn) and after restart finds exactly one run or none for that key, never two and never a key that answers 'not found'. Today a failed spawn leaves its directory behind, a directory without event 1 is invisible and never cleaned (core/src/store/derive.ts:67-71), and crash-left temporary files are never removed.
- A run's base commit is resolved when the submit is accepted and is written on the run record. Concurrent runs in one repository each start from the commit recorded for them, not from wherever the operator's HEAD is when their sandbox becomes ready.
  - honesty: Today the base is the host's HEAD resolved inside the worker after the sandbox is ready, up to 180 seconds after the submit, and is recorded nowhere durable (core/src/sandbox/worktree.ts:112, core/src/sandbox/run-sandboxes.ts:165, core/src/worker/run-loop.ts:210). A test moves HEAD between submit and sandbox start and the run still starts from the recorded commit; the branch-removal evidence rule (c10) reads the recorded base.
- The operator can configure a limit on concurrent runs per repository and per host; none applies by default. A configured limit is checked when the submit is accepted, and a submit past it is refused with a typed error naming the limit. A host that cannot take a run for lack of capacity refuses at submit where it can know, and otherwise fails the run with a reason that names the capacity.
  - honesty: With no limit configured no submit is refused for a limit; with one configured, a test sees the typed refusal at the limit. Today no bound exists and a gateway out of capacity shows up after the submit was acknowledged (core/src/harness/common/run-driver.ts:240-243).
- The run store carries a schema version. A 3.0 core reads run directories written by a 2.0 core and shows those runs; it never treats a record it cannot read as absent, and a run it cannot read never keeps a repository busy for ever. The upgrade procedure is stated: whether active 2.0 workers must finish first, and what the core does if they have not.
  - honesty: Today there is no store version, records and events are strictly validated, a new required field would make old records unreadable, an unreadable run with a live worker keeps its repository busy (core/src/runs/scan.ts:68-93), old workers keep rewriting run.json in the old shape (core/src/worker/run-loop.ts:168), and driver.json pins an absolute module path the worker imports after startup (core/src/worker/spawn.ts:157). A test starts a 3.0 core on a state directory holding finished and active 2.0 runs.
- A run that is waiting for its operator has a stated time rule: the question has its own time limit of 12 hours, configurable for less; the run's deadline pauses while the question is pending; and when the limit passes the run ends in a state that says the question went unanswered, not in a plain '`timed_out`'.
  - honesty: Today the deadline is absolute and keeps running, so a waiting run would become '`timed_out`' (core/src/worker/run-loop.ts:241-253), and both harnesses run with allow-all permissions and never ask (core/src/harness/claude-code/agent.ts:26, core/src/harness/opencode/client.ts:82). The probe that c7 depends on must show a harness asking and waiting before this is planned.
- Broker publishing is done by the core, which follows each run's log and keeps on disk how far it has published per run. After a restart it publishes what it missed, with the same event ids, and workers never connect to the broker.
  - honesty: The worker holds the append while it lives and the core appends only the orphan 'unknown' (core/src/worker/run-loop.ts:138-151, core/src/store/run-store.ts:62-72), so 'publish after append' needs a follower with a durable position. A test kills the core between an append and its publish and sees the event published once after restart.
- Finished runs' directories have a retention rule and the cost of submit, list and attach does not grow with the number of past runs: the core does not re-read and re-validate every event of every run on each call.
  - honesty: Today nothing deletes run directories or rotates events.jsonl and worker.log, every submit, list and agents call parses and validates every event of every run (twice per submit; core/src/runs/scan.ts:96-107, core/src/runs/service.ts:119-123), and each attach polls every 20 milliseconds (service.ts:213). A test seeds 1,000 finished runs and a submit still returns in under 2 seconds.
- The core exports one trace per run to a configured OpenTelemetry endpoint (the local Langfuse): spans for submit, sandbox setup, the harness turn, each tool call, each operator question, result collection and the terminal state, each carrying the run id, harness, model and duration. Export is off unless an endpoint is configured, comes after the on-disk append, and never blocks, slows or fails a run when the endpoint is down.
  - honesty: With the trace endpoint stopped, a run reaches the same terminal state and the same event log in the same time within measurement noise, and no call to the core blocks on the exporter.
- An operator can see load from the traces without reading run logs: how many runs and harness sessions are active per harness and per model at a moment, and how long each model call waited and ran. The capability report's active run count and the trace view agree.
  - honesty: With 3 runs active on 2 harnesses, the trace view shows 3 active runs split correctly by harness and model, and the capability report shows the same count at the same moment.
- The exporter adds no npm dependency: it sends OTLP over HTTP as JSON with Node's own fetch. The Langfuse keys reach the core as injected secrets and are removed from the environment before any worker starts, like every other secret.
  - honesty: core/package.json gains no dependency for tracing, and a worker's environment holds no Langfuse key.

## Honesty conditions

- Every clause of the announcement is covered by a requirement in this frame and by a test in the D2 acceptance suite; a clause without a passing test is reported as not delivered.
- The agents CLI is the only caller D2 is tested with. culture-rules and embodiment are named as later callers and nothing in D2 is built for them alone.
- No code path in D2 calls 'git worktree' or writes the host checkout or index. This holds only if q1 is answered 'sandbox clones are the isolation D2 means'.
- The contract tests that hold these guarantees in D1 still pass unchanged in meaning under API 3.0; a guarantee that 3.0 must weaken is listed in the spec as a breaking change, not changed silently.
- A test stops and kills the core while runs are active and asserts that no worker received a signal and each run still reached its own terminal event or deadline.
- With no network transport configured, the core opens no listening TCP socket (checked in a test), and the allow-list file is not reachable through any route, new or old.
- Each sentence of the after state maps to one requirement (c3, c4, c6, c7, c8, c9, c10); the part-two half is not claimed as delivered when only part one has shipped.
- Every file and line cited in the before state is re-read on main when the spec is exported, and a citation that has moved is corrected before export.
- The recovery tests issue #2 requires before archiving agent-lifecycle and cultureagent are named in the spec, and D2 states which of them it passes and which it leaves for D6.
- The mock stage uses the real CLI and the real core with the stub harness, as the D1 suite does, and a live stage reports NOT VERIFIED when a harness is unavailable, never a pass.
- The two hosts are mesh members that announced themselves. The acceptance record names them by role (host A, host B), never by host name; this replaces h19's 'named by the owner'.
- Tracked files name only the example node; no real host list or network address of the fleet appears in one. The rename from 'spark' covers the contract fixtures.
- The D2 part-two acceptance run passes with no chat server running on either host, and no code in core/ opens a connection to an IRC port or reads the mesh's link secrets.
- A test publishes a run whose output contains a marker string and shows the marker in no broker message. The broker accepts anonymous local subscribers (events-cli mosquitto.conf:49-61), while run logs on disk are mode 0600 because 'harness output may contain secrets' (core/src/store/files.ts:1-4).
- All submits are serialised today and each can wait up to 10 seconds for its worker (core/src/runs/service.ts:63-64, core/src/worker/spawn.ts:181), and OpenCode's cancel already takes 8.6 to 8.9 seconds of the 10 allowed with one run (docs/d0/d1-acceptance.md:167). The live stage measures both under concurrency; a miss is reported, not waived.
- With the default setting, a trace of a run whose events contain prompt text, output and tool results contains none of that text; no trace is sent to any address but the configured one.

## Success signals

- Part one passes a D2 acceptance suite in tests/acceptance/d2/ with a mock stage that always runs: (1) kill the core with 2 runs active in 1 repository, restart it, then steer one and cancel the other, and both take effect; (2) send the same submit 2 times with 1 idempotency key and count exactly 1 run, and the same key with a different request returns 'conflict'; (3) a run asks a question, the core restarts, the question is still pending, and 'agents runs answer' delivers it; (4) a submit past the concurrency bound is refused with a typed error; (5) 0 runs report 'succeeded' unless a worker wrote that terminal event.
- Part two passes on at least 2 real hosts: a submit from host A runs on host B and is steered and cancelled from A; with host B halted, every run that was active on it reads 'unknown' on A within a stated number of seconds and 0 read 'succeeded'; a submit to a host whose heat or gateway signal says hold is refused, and a missing signal reads 'unknown'.
- With 2 runs active in 1 repository, a third submit to another repository returns its run id in under 2 seconds, and a cancel reaches 'cancelled' in under 10 seconds on both harnesses.

## Scope / boundaries

- Per-run isolation stays what D1 built: each run works in its own sandbox clone made from a git bundle, and its commits return into its own `runs/<id>` branch. The host checkout and index are never written, and no git worktree is created on the host.
- The contract keeps its D1 guarantees: no AI SDK type appears in it, an unsupported action is refused with the typed 'unsupported' error naming the capability, the event cursor stays per run, gapless and never reset, a terminal state is final, and 'unknown' is never reported as success.
- Workers stay detached processes that never depend on the core: a core stop or crash never signals them, each one enforces its own deadline and writes its own terminal event, and the per-run control socket protocol does not change.
- Local use keeps its D1 security posture: the owner-only Unix socket, deny by default dispatch, and an exact-match allow-list that no API route can read or write. A network transport is added beside the socket, not in place of it.
- No real host list, address or network detail of the fleet appears in a tracked file, a test fixture or a published record. Fixtures, documents and tests use one example node, a Jetson Thor, in place of 'spark'; acceptance records name real hosts by role (host A, host B).
- Fleet membership does not travel over the chat mesh. The mesh's link password is neither reused nor read by culture-agents, and a stopped chat server changes nothing about which hosts are members or whether a run can be controlled.
- Events published to the broker carry lifecycle facts only: run id, event type, state, cursor and time. They never carry prompt text, harness output, tool results or an operator's answer. A subscriber that wants content reads it from the core by cursor, under the core's own access rules.
- Traces stay on the operator's own Langfuse and are not published to the broker or to another host. Whether a trace carries prompt text, harness output and tool results, or only names, sizes and timings, is a setting; the default carries no content, the same rule as broker events.

## Non-goals

- pause, resume, session continuation, agent-to-agent delegation and the 'artifacts' verb stay deferred after D2 and keep answering 'unsupported'. Issue #2's D2 gate names none of them.
- D2 does not edit a sibling repository from this checkout. A change D2 needs in a sibling is filed as an issue there and implemented as part of this project through a branch and pull request on that repository; D2 does not wait for it unless the plan says so. cultureagent and agent-lifecycle are cited and not archived.
- No workledger-cli integration in D2.
- The release workflow change (stage a dev version on pull requests, publish on main) is not part of D2; it goes out first as its own pull request.

## Assumptions

- A fleet is one core per host, each owning its own run store, sandboxes and repositories; a caller reaches a remote core over the network rather than one central controller driving every host.
- D2 does not depend on a message broker for control or for reading a run: waiting on a run stays a read of its per-run event log by cursor, and cross-host control is a request to that host's core. Run events are also published to the existing broker (events-cli) as a second transport, and a broker that is down never stops or fails a run.
- Every fleet host is set up by its operator before it can join: an OpenShell gateway, the model gateway on the port the sandbox policy expects, and a run image built on that host. The run image is single-architecture, and every probe so far ran on `x86_64`; an ARM host is not verified and reports its harnesses as unavailable until it is.
- Every process running as the core's user on a host is trusted: a worker's control socket has no credential, session or epoch, so any process of that user can steer or cancel a run, as it can today.
- Per-request model load (queue depth, tokens, concurrent requests per model and per machine) is the model gateway's to report, not culture-agents'. It is asked of lobes-cli as an issue and implemented from this project by pull request there, like the admit field.

## Scope exploration

- `s1` — `core/src/runs/service.ts + core/src/worker/spawn.ts (restart and live control)`: The only thing a restart loses is the in-memory map controls: Map<RunId, WorkerControl> (service.ts:60, filled only in submitNow at :171); the worker and its `<rundir>/control.sock` are intact. reconnectWorker (spawn.ts:201) already pings that socket and checks the PID, but only core/test/worker/worker.test.ts calls it. `live_control` is derived from controls.has(id) (store/derive.ts:334), so control is refused as unsupported('reconnect').
  - seeds: `c3`
- `s2` — `core/src/sandbox/worktree.ts + naming.ts (git handoff)`: worktree.ts contains no 'git worktree' command: prepare() bundles the base ref and clones it inside the sandbox (:107-159); collect() fetches `refs/heads/runs/<id>` back with a non-forced refspec and checks ancestry (:169-225). The only host write is that one ref. Sandbox name (ca-<sha256(runId)>), branch (`runs/<runId>`), bundle and `ssh_config` temp dirs are all per run id (naming.ts), so two runs on one repository collide on nothing at this layer.
  - seeds: `c5`, `c4`
- `s3` — `core/src/runs/service.ts:117-129 + runs/scan.ts:68-108 (busy rule)`: The one-run-per-repository limit is a policy check only: submitNow calls activeRunFor(scan, repo) and throws ControlError('busy'), keyed on the canonical repo string over the on-disk run store. No other admission limit exists (no global, per-agent, per-harness or per-host cap). The D1 acceptance suite asserts 'busy' (docs/d0/d1-acceptance.md:110-111), so those tests change with it.
  - seeds: `c4`
- `s4` — `core/src/runs/service.ts:141 + runs/control.ts:52 (idempotency key)`: The key is accepted on submit, steer and cancel and copied onto the run or action record, and nothing looks it up: a duplicate submit gets a new run id (or 'busy'), a duplicate steer is delivered twice. contract/README.md:301-313 says D1 does not promise deduplication and that it is 'planned for D2 and will be a versioned behaviour change'.
  - seeds: `c6`
- `s5` — `cultureagent/bridges/core/idempotency.py + server.py (prior art, local checkout 0.15.2, 2 commits behind upstream)`: The bridge reserves a key under a lock, replays the stored response to a duplicate, waits up to 10 s for an in-flight one and then answers 409 with Retry-After (server.py:318-350); one JSON file per sha256(key), written by temp file and rename (idempotency.py:40-100). It has no expiry, and it never compares the payload: the same key with a different request gets the old answer. D2 cites the reservation and replay, and adds the payload check and an expiry.
  - seeds: `c6`
- `s6` — `culture-rules/culture_rules/engine/actorport.py + actors/agent.py (the D4 caller)`: ActorPort.invoke passes one `idempotency_key` per run and step, identical across attempts, hosts and restarts, and requires the adapter to deduplicate on it; an adapter that cannot must set `supports_idempotency_key` = False and the step then fails as `unsafe_retry`. ## Decisions

- D2 ships as control API version 3.0, one deliberate major bump that carries every contract change of the gate together, instead of a series of bumps.
- D2 is delivered in two parts. Part one stays on one host: reattach after restart, concurrent runs in one repository, idempotent submit, operator questions, branch cleanup and the three known gaps. Part two adds more than one host: a network transport with authenticated callers, placement and admission, and halted-host detection. Part one does not wait for the decisions part two needs.
- Fleet membership is announced by the host itself: a core running as a daemon, container or service notifies that it is part of the fleet. Today the fleet is the whole mesh. The machines are not named in this public repository.
- D2 publishes run events to the existing message broker (events-cli) because later callers need the events.
- Steer stays non-preempting in D2 and is documented as such. Interrupting a turn is part of pause and resume, which come after D2.
- A fleet member needs a credential. The mesh already recognises its members with a shared secret; D2 extends that toward best practice, either public and secret keys or OS-based authentication (the user account). Which of the two is still open.
- One repository can exist on more than one host of the fleet, as lobes-cli does.
- Sibling-repository changes that D2 needs are filed as issues and implemented as part of this project, through branches and pull requests on the sibling repository. The first is an admit field with a timestamp on the lobes gateway status.
- There is no implicit limit on concurrent runs. The operator can configure one. The real limit is inference capacity when running local models, which the gateway signal reports and which cloud models remove.
- A pending operator question has a time limit of 12 hours, configurable for less; the run's deadline pauses while the question is pending.
- The example node in fixtures, documents and tests is a Jetson Thor, to show how an edge machine or a robot behaves as a fleet member; 'spark' is replaced.
- Run logs and attach streams that cross hosts are only restricted to callers allowed to read the run, not redacted; a sensitivity mark is added if it is cheap.
- Observability is part of the D2 design. Run and model activity is traced to a Langfuse instance the operator runs locally. (Owner, 2026-11-26: 'We should have observability and it should be part of the design. We can run langfuse locally.')
