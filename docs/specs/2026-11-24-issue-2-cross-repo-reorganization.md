# issue-2 cross-repo reorganization

> AgentCulture has one direct agent control plane (culture-agents), one communication product (culture-chat), one workflow engine (culture-rules), and independently deployable experience apps (embodiment/Gwen): no duplicated harness or dispatch managers, no requirement that agents join chat, and no lost realtime or safety guarantees.
> instruction: Verify against issue #2's success criterion; this spec delivers only its D0 and D1 part, and the deferred non-goals name the rest.

## Audience

- Operators and agents that need to hand work to a coding-agent harness on one host without a chat server: the human operator at the 'agents' CLI, and programmatic callers (other agents, later embodiment and culture-rules) using the same control API.
  - instruction: Check that every D1 verb is reachable both from the 'agents' CLI and from the core's local JSON API with identical semantics.

## Before → After

- Before: culture-agents is a template scaffold with no control-plane code. Dispatch exists only as cultureagent's one-shot bridges, which cannot steer or answer and report an in-flight run as unknown after a restart, and as IRC-coupled resident daemons that need the chat server up to start.
  - instruction: Cite cultureagent docs/bridges.md:172-173 and `culture_core`/cli/agents.py:766-768 in the D0 inventory.
- After: On a single host, 'agents runs submit' hands a task to a TS core daemon and returns a durable run ID; the run can be listed, shown, attached to as a live event stream, steered mid-run and cancelled, against real harnesses, with no chat server running; run state is stored on disk and read back truthfully after the daemon restarts.
  - instruction: Run the D1 acceptance script on this host with the culture server stopped.

- Because every merge to main publishes to PyPI, partial control-plane code reaches users before D1 is complete; each PR therefore keeps unfinished verbs out of the registered CLI or marks them '(planned)', and the published capability document never claims an unbuilt capability.

## Decisions

- Worktree branches for runs are named `runs/<id>`, not `agent/<id>` (issue #2 comment 2 section 5; confirmed comment 3 item 10); embodiment#129's `agent/<id>` proposal is superseded.
- The culture-agents core is TypeScript. The Python 'agents' CLI is the controller of that worker, used like an API client, and agentfront provides its agent-facing surfaces.
- This work's target is D1: a single-host spike where an agent is dispatched, inspected, steered and cancelled without chat, through real harnesses, with a stable run ID and durable status. The D0 inventory and contract are built as part of it.
- For this specific work, sibling repos may be changed directly through branches and PRs, not only tracked issues.
- The workspace map (the product and repo layout now described only in the untracked /home/ori/git/CLAUDE.md) lives in the culture repo. codexd, the Codex daemon, may be moved as needed.
- Packaging of the seam is two packages: the TS core is published to npm and the Python 'agents' CLI to PyPI, each versioned and released on its own. The core runs as a supervised local daemon on Node >= 22 and exposes a versioned JSON API with an SSE event stream over a Unix socket; the JSON schemas in this repo are the source of truth for both, and the CLI checks the core's API version on connect and refuses an incompatible one with an environment error (exit 2).
- agentfront is approved as a runtime dependency of the Python CLI, replacing the code cited from teken; further runtime dependencies may be approved case by case. This amends culture-agents/CLAUDE.md's zero-third-party-dependency rule.
- After a daemon restart in D1, surviving per-run workers are left running and their state is reported from the on-disk event log; live control of those runs returns in D2.
- The TS core is published to npm as @culture.dev/agents, following embeddings-tumbler's publish workflow (npm provenance via id-token, PyPI publish waits for npm so a failed npm publish leaves nothing published).
- The sandbox under the harness layer is a known sandbox solution, with NVIDIA OpenShell preferred, not a home-written local provider without isolation.
- OpenShell may be installed on this host at user level, with its local gateway started, when the probe task runs.
- Working-tree handoff for a run: the repository enters the OpenShell sandbox as a git bundle and is cloned there; the host fetches the run's commits straight from the sandbox over SSH into a `runs/<id>` branch. The host checkout is never written by a harness.
