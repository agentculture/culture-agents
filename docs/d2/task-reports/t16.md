# Task report: t16, CLI idempotency keys, retry and `runs answer`

## What I built

- `culture_agents/cli/_commands/runs.py`: submit, steer and cancel always send an
  `idempotency_key`: the user's, or `cli-<uuid4 hex>`. `--json` output carries it as a
  top-level `idempotency_key` next to the core payload (added after validation, so the
  core response is still validated unchanged). Text shows an `idempotency key:` line only
  when the CLI generated it. New verb `runs answer <run_id> --question Q [--answer T]
  [--choice a,b] [--decision approve|deny]`, with the caller flags and an optional
  `--idempotency-key`. It is sent once and never retried. Typed errors get
  answer-specific remediation (`conflict`: never retried or replayed; `unsupported`:
  only the stub harness can ask; `unavailable`: check `runs show` first).
- `culture_agents/cli/_client.py`: `post_keyed` retries when the core did not answer
  (timeout, refused or reset connection, `unavailable`) up to 3 attempts, with the identical
  body and key (honours `retry_after_ms`). Other typed errors are final. The last failure's
  remediation names the key to reuse. `DEFAULT_TIMEOUT` is a module constant (testable).
  Response validation is unchanged (`post` -> `_json` -> `_contract.problem`, invalid is
  `internal`, exit 2).
- `culture_agents/explain/`: catalog entry for `runs answer`; submit/steer/cancel entries
  describe the keys; root and `runs` pages list the verb.
- `_app.py` registers the verb; `contract/api.json` and `contract/README.md` no longer say
  "planned" for the CLI of `runs.answer`.
- Tests: new `tests/test_cli_keys.py`; `tests/fake_core.py` gained an answer route, per-POST
  stalls and a count of distinct keys per path.

## Acceptance criteria

1. Keys: **proven against the fake core.** `test_every_keyed_verb_sends_a_generated_key_and_prints_it`,
   `test_a_given_key_is_used_unchanged`, and `test_after_a_timeout_the_cli_retries_with_the_same_key_and_one_run_results[submit|steer|cancel]`
   (first POST takes effect but answers after the client timeout; the retry has the identical
   body; the count of distinct keys, which is what a key-honouring core would create, is 1).
   The "1 run" is counted by the fake core's distinct keys, not by the real daemon; the real
   core's replay is proven by t6's tests. I did not add a real-daemon timeout test.
2. Answer: **proven** by `test_answer_*` in `tests/test_cli_keys.py` (delivery and request
   schema, typed errors `conflict` and `unsupported` in text and `--json`, no retry, also none
   after a timeout). Explain entry exists; teken strict explain checks pass (except the
   network build check, see above).
3. Validation: **proven** by `test_an_invalid_core_response_is_internal_exit_2` (all four
   verbs, exit 2, `error_code: internal`), plus the existing validation tests.

## Choices and assumptions

- Answer takes `--choice` as one comma-separated string (no repeatable flag).
- Answer sends a key only when the user gives one; it is never generated for it.
- Retry covers every `unavailable` (including core-sent ones), 3 attempts in all.
- Existing tests updated, none deleted: `tests/test_cli_runs.py` (submit/steer/cancel
  expectations now account for the generated key and the extra text line).
- Left unchanged on purpose: core code, the wire contract schemas.
