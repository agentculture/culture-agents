# TASK-REPORT t22: fleet members (announcement, the member list, unique node names)

## What I built

Decision 3 of `docs/d2/part-two-design.md` (announcement), as that record
recommends, on t21's transport and trust list. The numbers are the record's:
announce every 5 s, drop after 15 s of silence, sweep every 1 s, and a 5 s
timeout on every call.

- `core/src/fleet/members.ts`: the member list, built from announcements only.
  - A peer is listed only after an announcement from a key the transport
    authenticated, and only under the node name the trust list gives that key.
  - It is dropped when silent for more than 15 s (a read never shows it after
    that, and the 1 s sweep logs the drop), or at once on `leaving`.
  - The clock is monotonic and injected in tests. The sender's clock is never
    read.
  - Refused with `conflict` and reported (the core's log, at most once a minute
    per claim, plus a bounded `refused` list of the newest 32): an announcement
    from this core's own key; one that claims a name other than its trust-list
    name; one that claims this core's own name with another key; one that
    claims a name still held by another listed key.
- `core/src/fleet/announce.ts`: the announcer.
  - Every interval it sends `POST /v1/fleet/announce` to each address in the
    local address list, in parallel, one connection per call.
  - Limits: a timeout of at most 5 s, a 16 KiB cap on the reply, and no second
    call to an address while one is in flight.
  - The reply, which is the peer's own announcement, is checked against the
    schema and goes into the member list. Outcomes are logged when they change.
  - A clean stop lets the round in flight settle (at most 1 s), then sends
    `leaving` with a 1 s timeout.
- `core/src/fleet/peers.ts`: the local, untracked address list
  `${XDG_CONFIG_HOME:-$HOME/.config}/culture-agents/fleet/peers.json`.
  - A JSON array of `"<ip>:<port>"` strings. IP literals only, so a name is
    refused and nothing is resolved. Ports 1 to 65535, at most 64 entries,
    read with the trust file's 1 MiB cap, and read again every round.
  - An invalid file stops the core at start (exit 2), through
    `loadFleetConfig`. If it turns invalid at runtime, the core announces to
    nobody and logs why, once per change.
  - `config.ts` now has `parseAddress`, shared with `parseListen`, whose
    behaviour is unchanged.
- `core/src/fleet/index.ts`: `createFleet` (the member list, the listener, the
  announcer and the sweep) replaces `startFleet`.
  - Members are served `GET /v1/version`, `POST /v1/fleet/announce` (body
    capped at 16 KiB, checked against the schema) and `GET /v1/fleet/members`.
  - A refused announcement gets 409 with `fleet.json#/$defs/announce_refusal`.
- Wiring:
  - `core/src/daemon/main.ts` creates the fleet before the socket listens and
    passes the member list to the daemon.
  - The local route `fleet.members` (`GET /v1/fleet/members`) is in `routes.ts`
    and `daemon.ts`. With the transport off it answers `transport: off` and two
    empty lists.
  - `readJsonBody` in `daemon/http.ts` takes an optional byte cap. The default
    and its message are unchanged.
- Contract, a MINOR addition (`api_version` 3.0 → 3.1):
  - The new file `contract/fleet.json` holds the root `MemberList` and the
    defs `member`, `refusal`, `fingerprint`, `announcement` and

  - New route `fleet.members` in `api.json`, 6 valid and 9 invalid fixtures,

  - In `contract/README.md`: the version, a Files row, a Routes row and a new

  - No 3.0 shape changed.
  - The version fixtures, the `version.json` description and the wheel's
    force-include list (`pyproject.toml`) follow.
- CLI:
  - `agents agents list` also calls `GET /v1/fleet/members`. Text shows the

  - `CLIENT_API_VERSION` is 3.1, `_contract.TARGETS` has `member_list`, and

## Acceptance criteria

1. **Proven.** A core appears in the member list after it announces itself,
   and leaves it within the stated time after it stops or goes silent. The list
   is built from announcements only.
   - `core/test/fleet/members.test.ts`, with an injected clock:
     - nobody is listed before an announcement, trusted or not;
     - a member is listed under its trust-list name;
     - it is still listed at 15 000 ms and gone at 15 001 ms, and the sweep
       logs the drop;
     - every announcement restarts the silence, and a returning member is
       listed again;
     - `leaving` drops it at once.
   - `core/test/fleet/announce.test.ts`, with two real fleets on loopback:
     - each core lists the other after one announcement (within 5 s), the
       second through the reply;
     - a clean stop leaves the list empty before `stop()` returns;
     - silence drops a member at 15 s on the listener's injected clock, and it
       is listed again at its next announcement;
     - the announcing core drops a core that went silent.
   - `tests/acceptance/d2/test_fleet_members.py`, with two real built cores and
     the real CLI:
     - each lists the other, and a SIGTERM stop leaves the list;
     - a SIGKILL'd core is dropped by silence, no sooner than 9 s after the
       kill. Generous bounds here, because the machine is loaded.
2. **Proven.** An announcement from a core whose node name is already held by a
   different key is refused and reported to the operator.
   - `announce.test.ts` and the acceptance test: a second core started with
     thor's name and a different key gets 409, is never listed, is in
     `refused` with its fingerprint and reason, and is logged by the refusing
     core ("refused an announcement (conflict)"). The refused core logs the 409.
   - The acceptance test also checks that `agents agents list` prints
     "refused announcements (1)".
   - `members.test.ts` covers the other conflicts:
     - a name other than the key's trust-list name;
     - a name still held by a listed key until that key leaves or goes silent
       (retryable);
     - this core's own key;
     - counting, log rate and the 32-entry bound.
3. **Proven.** `agents agents list` shows members with `--json`, and no host
   list exists in any tracked file.
   - `tests/test_cli_fleet_members.py` (text, `--json` under `fleet`,
     transport off, a contract-breaking list refused with exit 2, terminal
     escapes neutralised) and the updated `tests/test_cli_agents.py`.
   - `core/test/fleet/route.test.ts` covers the local route.
   - The acceptance test reads `--json` from real cores.
   - `tests/test_fleet_no_host_list.py`: no tracked file is named `peers.json`
     or `trust.json`. No tracked file holds an `ip:port` address that names a
     host; loopback, the unspecified address and the RFC 5737 documentation

## Choices and assumptions (read these)

- **API 3.1.** 3.0 was released in 0.16.0, and the README says a new route is
  MINOR and bumps the version. So the contract is now 3.1. A 3.0 client works
  with this core, and this 3.1 CLI refuses a 3.0 core (a test was added).
  - t23's plan text asks for a test "with a core that reports 3.1". That is now
    this core's own version, so t23 will need a 3.0 or 3.2 peer for that test.
- **`announce_refusal` instead of `error.json`'s `conflict`.** In 3.0,
  `conflict` requires `run_id`, and changing that would be MAJOR. A refused
  announcement therefore gets HTTP 409 with its own shape,
  `{code: "conflict", message, retryable}`, in `fleet.json`.
- **A second node name in tests.** I departed from "the only node name in
  tests is thor."
  - c40 requires a core to refuse a peer that claims its own name with another
    key. Two cores both named thor therefore cannot list each other.
  - The positive listing tests name the listening core `xxxxxxxx`. That is
    length-boundary filler which `check-example-node.py` treats as naming no
    node, and it is not a host name. Each test explains this in a comment.
  - The conflict tests use two thor cores, as the spec's c40 honesty line
    describes.
- **This core's own key is refused** (a core is not its own member). This
  matters when its own address and key are in its own lists. The record does
  not cover it.
- **A name held by a listed key** is refused to a new key until the old key
  leaves or goes silent. This happens when a trust entry is replaced while the
  old key's core still runs. My reading is that c40 forbids two live holders.
- **Clean-stop detection is for the addresses the stopping core knows.** A core
  that knew it only from its replies drops it by silence, within 16 s. This is
  documented.
- **`agents agents list --json`** is no longer a pure single-route passthrough.
  It is the `agent_list` payload plus `fleet`.
- **Members can read the member list over the transport** (the record says the
  list is readable by "the local socket owner and authenticated members").
- **The core logs addresses** (for example "cannot announce to `<ip>:<port>`")
  only to its own stderr.
- **Not done here:** "its active runs read unknown" from the spec's honesty
  line, which belongs to t25 (unreachable view). Remote calls belong to t23.
